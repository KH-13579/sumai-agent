01前提と全体像

法規チェックAI は、間取り3案に対して建ぺい率・容積率・高さの適合を判定し、数値計算では判断できない項目を要確認フラグとして立てます。要件定義書 §7.6（LAW-1〜4）に対応します。

初めて動かす場合は 02 章から順に進めてください。すでに構築済みなら 03 章（起動手順）だけで足ります。人前でデモを行う場合は 05 章（応答キャッシュ）を必ず読んでください。

05LLM応答のキャッシュ

CPU 推論では間取り生成 1 回に 13〜39 分かかります。この待ち時間は実演では成立しません。そこで LLM の応答を一度だけ実機で取得してファイルに保存し、2 回目以降はそのキャッシュを返します。要件定義書の NFR-06 オフライン再生が要求している仕組みで、副作用として NFR-01 デモ再現性（同じ入力に必ず同じ応答）も満たされます。

モデル変更やメモリ増設との違い

軽量モデルへの切り替えやメモリの増設は待ち時間を短くするだけで、CPU 推論である限り数分〜数十分は残ります。待ち時間を 0 にできるのはキャッシュのみです。ネットワーク断や Ollama の停止でもデモが完走するという利点も、キャッシュにしかありません。さらに 7b への変更は間取りが 1 案に減るという別の問題を生みます（10 章）。

4 つのモード

.env の SUMAI_LLM_CACHE で切り替えます。

値動作使う場面
off常に実機の LLM を呼ぶ既定。開発中
autoキャッシュがあれば返し、無ければ実機を呼んで保存デモ準備・デモ本番
replayキャッシュのみを使う。無ければエラーデモ前の最終確認
record常に実機を呼んでキャッシュを上書きプロンプト変更後の作り直し

auto が実用上の中心です。キャッシュが外れても実機にフォールバックするだけなので、デモが止まることがありません。逆に replay はキャッシュが 1 つでも欠けていればその場で失敗するため、事前確認に向いています。

手順

  1. デモシナリオのキャッシュを作る

    初回だけ実機を走らせます。数十分かかるので裏で流しておいてください。ブラウザに張り付く必要はありません。

    ターンごとの所要時間が出力されるため、モデル比較のベンチとしても使えます。--model qwen2.5:14b を付ければ .env を書き換えずに別モデルを計測できます（既定の 3b で品質が足りない場合の比較用。7b でも間取りが 1 案に減った実測があります → 10 章）。

  2. キャッシュだけで完走するか検証する

    --verify は SUMAI_LLM_CACHE=replay で走ります。Ollama を止めてから実行すれば、オフラインでデモが成立することを確実に確認できます。

  3. 本番は auto で起動する

    .env を SUMAI_LLM_CACHE=auto に書き換えてアプリを起動すると、キャッシュ済みのシナリオは即座に応答が返ります。

キャッシュが命中する条件

キャッシュキーは モデル名 ＋ JSON モード ＋ 全会話履歴のハッシュです。この 3 つが作成時と一致したときだけキャッシュが使われます。

06システムの動作

LangGraph のグラフ形状は次のとおりです。破線の逆流は法規NG 時の自律修正ループ（既定は無効）です。

3つの接続点

A POST_HEARING_STEPS — 実行順を宣言する唯一の場所

要件が揃った後に走る専門エージェントは、すべてこのリストで宣言します。エージェントを追加する際にグラフの分岐を書き換える必要はなく、AgentStep を1行足すだけで済みます。is_enabled で条件付きスキップ、route_override で逆流（法規の自動修正がこれを使用）ができます。

B reply_sections と compose_node — 応答の合成

各エージェントは reply を直接書かず、reply_sections に markdown を1セクション push します。終端の compose_node が連結・重複排除（同一エージェントは最後の1件のみ採用するため、修正ループで2回走っても重複表示されません）を行い、成果物がある応答にだけ免責を付与します。

C GET /api/artifact/{session_id} — 下流へのデータ入口

LangGraph のチェックポイントからセッションの成果物を取り出し、統合 JSON として出力します。見積AI を接続する場合、グラフの内部を理解する必要はなく、これを読むだけで足ります。

07法規チェックの中身

中核となる設計は判定を純粋な算術で行い、LLM を介在させないことです。LLM の役割は land_info の自由文から敷地面積・用途地域・道路幅員を抽出する1点のみです。これにより同じ入力に対して常に同じ判定文が返り、LLM の揺れでキャッシュ作成時に破綻することがありません（NFR-01）。

自動判定（LAW-2）

項目判定式根拠
建ぺい率建築面積 ÷ 敷地面積 ≤ 指定建ぺい率第53条
容積率延床面積 ÷ 敷地面積 ≤ min(指定容積率, 前面道路幅員 × 法定係数)第52条
絶対高さ制限推定高さ ≤ 10m（低層住居専用・田園住居のみ）第55条
用途制限工業専用地域は住宅不可 → ng別表第二

容積率が要点です。幅員 12m 未満の場合、基準容積率が指定容積率より厳しくなるのが通例なので、両者の小さい方を採用します。法定係数は住居系が 4/10、その他が 6/10 です。角地・防火地域の緩和は一律見込みません（安全側の判定）。

自律修正ループ（既定は無効）

SUMAI_LEGAL_AUTOFIX=1 のとき、法規NG が出ると上限値を制約として間取り生成AI へ差し戻し、再生成して再判定します。無限ループ防止のため最大1回で打ち切ります（NFR-07）。実機で確認済みの挙動：planning は2回呼ばれ、敷地照会は1回のみ（再利用）、応答に重複表示はありません。

既定を無効にしているのは、間取り生成が2回走るため所要時間が倍になるからです。デモの見せ場として使うときに有効化してください。

08エージェントの追加

見積AI（EST-1〜4）とメーカー推薦AI（MKR-1〜6）は以下の5手順で接続できます。グラフの分岐ロジックを触る必要はありません。

  1. 出力スキーマを定義する

    app/schemas/ に追加します。legal.py と同じ書式（Pydantic v2 ＋ 日本語 description）に揃えてください。

  2. エージェント本体を実装する

    app/agents/estimate_agent.py に2つの関数を置きます。run_estimate() が構造化結果を返し、build_estimate_reply() が説明文を返します。LLM は引数で受け取る純関数にすると、テストでモックできます。

  3. state にスロットを追加する

    app/agents/state.py の SumaiState に、結果の格納先を1行追加します。

  4. ノードを書き、1行登録する

    ノード関数は結果を state のスロットに入れ、説明文を section("estimate", "概算見積", markdown) で返します。連結と免責の付与は compose_node が一括で行います。

  5. 外部インターフェースに繋ぐ

    app/schemas/artifact.py と app/api/chat.py の ChatResponse にそれぞれ1項目追加します。

AgentStep の2つのオプション

is_enabled が False を返すとそのステップを飛ばします（条件付き実行）。route_override がノード名を返すとそこへ遷移します。生成→検査→修正の逆流に使うもので、見積AI の「予算超過 → 再生成」も同じ口を再利用できます。

14b の 3 倍のばらつきは CPU の速度変動ではなくメモリ不足によるページングが原因です。14b は 9 GB の重みに加えて KV キャッシュを必要とするため、実メモリが 16 GB を下回る環境では所要時間が大きく揺れます。

軽量モデルへの変更は解決策になりません

同一シナリオ（ペルソナC）を qwen2.5:7b で計測したところ、間取りが 3 案ではなく 1 案しか生成されませんでした。速度は 2〜6 倍になりますが、指示追従が落ちて要件（3 案提示）を満たせません。デモは品質を確認したモデル ＋ 応答キャッシュという組み合わせで行ってください。開発中は qwen2.5:3b に統一していますが、3b は 7b よりさらに小さいため 3 案提示の品質は要検証です。

取れる対策

対策効果代償
応答キャッシュ（NFR-06）
実装済		デモ時は秒単位。毎回完全に同一。オフラインでも完走事前に一度作成する時間が必要 → 05 章
keep_alive を延ばす毎回の約 100 秒のロードを省けるモデルがメモリを占有し続ける
使用メモリを増やす最悪ケースのばらつきが解消し、下限付近に安定する下限そのものは変わりません
出力トークンを削る時間がほぼ比例して短縮（現状 num_predict=4096）案の説明文が短くなる
小さい量子化（q3_K_M 等）約 7 GB でメモリ圧迫が減る重みの精度がやや下がる
qwen2.5:7b に変更間取り生成が 366 秒に短縮案が 1 案に減る（上記）
メモリ増設について誤解しやすい点

メモリを増やしてもばらつきが消えるだけで、下限は変わりません。762 秒という下限は CPU の演算能力で決まるためです。したがってメモリ調整の価値は「所要時間が予測可能になること」であり、「デモに使える速度になること」ではありません。デモに使える速度にする唯一の方法は 05 章の応答キャッシュです。

② 坪／㎡ の単位取り違え — 3層の防御を実装済み

実機検証で見つかった実際の問題です。「35坪」（≒116㎡）という要望に対し、qwen2.5:14b は 約35㎡（約10.5坪） と出力しました。坪の数値をそのまま㎡欄に書き、さらに階数まで同じフィールドに混入させていました。部屋面積の合計は 65㎡ 以上あり、「延床 35㎡」と自己矛盾しています。

当時の結果

法規チェックの算術は入力に対して正しく動いていましたが、入力そのものが壊れていたため、建ぺい率 11.6%・容積率 21.2% となり3案すべてが「✅ 適合」になりました。誤った安心感を与えていたわけで、法規チェックとして最も避けるべき状態です。

3回の実測により、プロンプトだけでは信頼できないことが確認されました。

#プロンプト出力結果
1元のまま35 / 40 / 38㎡単位が誤り。階数も混入
2単位ルールを追加116㎡ ×3単位は直ったが3案が同一に
3差別化ルールも追加30 / 40 / 35㎡差別化されたが単位が誤りに戻る

そこで要件定義書（KH案 §9.2.2「再アライメント＝ルールベースでの補正」）の方針に沿い、3層構成にしました。

1 プロンプトの強化

planning_agent に明示：1坪 = 約3.31㎡、floors に面積を書かない、3案の面積に差をつける、延床は部屋面積の合計を上回る。

2 決定論的な単位補正

area_utils.normalize_total_floor_area()：部屋面積の合計（畳→㎡換算）が延床を超えている場合、数値を坪として再解釈します。再解釈して整合し、かつ戸建てとして妥当な範囲（40〜400㎡）に収まる場合のみ補正します。補正した事実は summary に明記し、隠しません。

3 整合性チェック（最終防衛線）

legal_rules.check_plan_consistency()：補正できない矛盾データは、建ぺい率・容積率を unknown とし、high「間取りデータの整合性」フラグを立てます。決して「適合」とは言いません。

結果として、以前の壊れたデータは正しく3件の unknown になります。実機の最終出力は 120 / 135 / 130㎡ で、3案が差別化され、全案が整合し、判定も確定しました（建ぺい率 40〜45%／上限50%、容積率 72.7〜81.8%／上限100%、高さ 8m／上限10m）。

③ リポジトリ管理：.env が git 追跡下にあります

既存の問題で、今回の変更で持ち込んだものではありません。ただし REINFOLIB_API_KEY が .env に入ったため、実際のキーを記入した時点でコミットされてしまいます（NFR-03「API キー等をリポジトリに含めない」に違反）。また .pyc が1つ追跡リストに残っています（.gitignore に *.pyc はありますが、既に追跡済みのファイルには効きません）。

他メンバーの checkout に影響します（各自 .env.example から .env を作る必要があり、README に手順は記載済み）。そのため独断では実行していません。
