## 1. 背景・目的

### 1.1 背景
社内コミュニティ活動（業務外研究会）として、生成AI・AIエージェントを活用した新規ビジネスモデルのプロトタイプを検討する。テーマは住宅領域（BtoC）。

### 1.2 目的
家を建てたい個人に対し、AIエージェントがヒアリングを行い、**間取り案・概算見積・法規チェック**を一気通貫で提案するサービスのコンセプトを、動くモックとして実証する。利用者は成果物を住宅メーカー／工務店に持ち込む使い方を想定する。

サービス構想（調査チーム構想）としては、さらに**部材表・推奨建設会社／工務店の提示・3D 構想図**までを含む一気通貫提案を目指す。ただし部材表・推奨業者提示は技術的な実装方法が未定のため、モックでの扱いは §2.2.1 に整理する（3D 構想図は FR-10）。

### 1.3 プロジェクトの目標成果物
本書のゴールは本番サービスではなく、以下 3 点の成立である。

1. **パワポ紹介スライド** … 住宅業界のビジネスが本アプリ導入で before/after どう変わるか（最重要）
2. **デモ動画**
3. **モックアプリ** … デモを最低限動かせる程度

> 【critical】本書の要件はすべて「上記 3 成果物に寄与するか」で優先度判定する。デモに映らない機能は原則 Could 以下。

## 2. スコープ

### 2.1 対象範囲（やること）
- ヒアリング対話（不足情報の能動的な聞き返しを含む）
- 敷地・法規情報の自動取得（対象 1 自治体に限定）
- 間取り案の生成（既存優良事例の検索＋入力条件への適応 = retrieve-and-adapt 方針）
- 法規チェック（数値計算できる項目のみ自動判定、それ以外は要確認フラグ）
- 概算見積（坪単価ベース）
- **自律修正ループ**（チェック不合格 → 間取り修正 → 再チェック）
- **機械可読アーティファクト**（業者に渡せる構造化された設計・仕様ファイル）の出力

### 2.2 実装方法未定（やるが方式未確定）と対象外（やらないこと）

#### 2.2.1 やるが技術的な実装方法は未定

調査チーム構想（`survey-team/調査チーム検討状況.md`）の一気通貫提案に含まれる以下の項目は、**サービス構想としては対象に含める**。ただし技術的な実装方法が未定のため、本モックでは代替手段で対応し、方式が確定し次第 FR に昇格する（→ U-07）。

| 項目 | 実装方法が未定である理由・現状の検討状況 |
|---|---|
| 部材表 | 見積は坪単価ベースであり、部材表を支えるデータ層が現状存在しない（SKU 単位〔建材住設商品マスタ API〕は粒度過剰・要契約）。部材表に必要な粒度のデータ調達方法が未定。モックでは概算見積（FR-05）で代替 |
| 推奨建設会社／工務店の提示 | 実装可能な業者 DB が現状存在しない。推奨・マッチングの実現方法が未定。モックでは機械可読アーティファクトの受け渡し（FR-07。将来の A2A による業者接続の布石）で代替 |

- なお、構想に含まれる 3D 構想図は FR-10（Could）としてスコープ内に整理済み。

#### 2.2.2 対象外（やらないこと）

| 項目 | 理由・経緯 |
|---|---|
| 精緻見積もり | 実数量（BIM 相当）が必要で、概算入力と循環依存になる。「概算」と明記して出す |
| 資金計画（ローン試算） | 金利・返済期間の前提定義が必要で、坪単価概算とは別課題。（FR-05 は「概算見積」に限定） |
| 監査エージェント（外部 LLM による出力検証） | 厳密性が要る検証は法規チェックの決定的計算が担うべきで、LLM 監査は精度担保にならず構成を複雑にするのみ。**2026-07 不採用を決定** |
| 全国の法規対応 | 斜線・日影・自治体条例は自治体ごとの非統一データでデジタル化されていない。1 自治体限定（§6 FR-04） |
| 本番品質全般 | 認証・課金・個人情報管理・スケーラビリティ・運用監視はモックに不要 |

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| retrieve-and-adapt | ゼロから間取りを生成せず、既存の優良間取り（テンプレ）を検索し、入力条件に合わせて改変する方式 |
| 自律修正ループ | 生成 → 検査（法規・予算） → 不合格なら修正 → 再検査、をエージェントが自律的に回すこと。本モックの技術的な主役 |
| 機械可読アーティファクト | 間取り・仕様・制約・チェック結果を構造化した、業者側システム（将来は業者側エージェント）が読めるファイル |
| 要確認フラグ | 自動判定できない法規項目（斜線・条例等）について「専門家確認が必要」と明示する出力 |
| ポリストア | 役割の異なる複数形式（構造化／グラフ／ベクトル）のデータストアを併用する構成 |

| 項目 | A：初めて検討層 | B：建替え・住替え層 | C：土地ありこだわり層 |

| 年齢 | 30〜35歳 | 45〜55歳 | 35〜45歳 |

## 5. ユースケース／デモシナリオ

**【未確定 — 調査チームと協議のうえ確定する（U-01）】**

協議で決定すべき項目（決定後、本節にデモ台本として記載する）:

- [ ] 主ペルソナ（A／B／C のいずれか）
- [ ] 土地の有無（有りにすると法規チェック・敷地照会が実演できる）
- [ ] 対象自治体（1 つ。法規データ準備の前提。※**GIS データが整備・更新されている自治体の中から選ぶ**こと（先に自治体を決めてから可否確認する順序は手戻りする）。PLATEAU 整備有無も併せて確認（FR-10 用））
- [ ] デモの起点（初回入力に何を与えるか）と終点（何が出たらデモ終了か）
- [ ] 見せ場の順序（ヒアリング → 生成 → 法規 NG → 自動修正 → 合格 → アーティファクト出力、を推奨）
- [ ] before/after スライドとの対応関係（スライドで訴求する場面がデモに登場するか）
- [ ] 平屋か 2 階建てか（2 階建ては階属性・階段の階間整合の表現が必要 → U-04。平屋なら回避できる）
- [ ] 高さ NG を演出する場合、絶対高さ制限（10m/12m）のある低層住居専用地域を選ぶ（他の用途地域では高さチェックが自明合格になり見せ場にならない）
- [ ] デモで使う住所の選定（実在の個人宅を避け、公共施設・更地等の問題のない地点にする。動画・スライドに映るため）
- [ ] 敷地ポリゴンのプリセット作成（登記所備付地図データから対象自治体の 1 筆を抽出。§10）
- [ ] 土地なしペルソナ（A 層）を選ぶ場合の代替演出（想定エリアの代表地点で照会する等。FR-02/04 の見せ場が痩せる問題への対処）

## 6. 機能要件

優先度: **Must**（これが無いとデモが成立しない）／**Should**（デモの説得力を上げる）／**Could**（余力があれば）。

| ID | 機能 | 優先度 | 概要 |
|---|---|---|---|
| FR-01 | ヒアリング対話 | Must | 入力の曖昧・不足をエージェントが検知し、何を聞き返すか自律判断する（能動ヒアリング） |
| FR-02 | 敷地・法規情報の自動取得 | Must | 住所・地番から用途地域・建ぺい率・容積率を不動産情報ライブラリ（GIS）で自動取得 |
| FR-03 | 間取り案生成 | Must | retrieve-and-adapt。2 段検索（ハード制約フィルタ → 形状・条件の類似度ランク）→ LLM による局所改変 → 決定論的な幾何検算（重なり・境界内包・面積・隣接整合。不合格は自動リトライ）。方式詳細は §9.2（表現形式・方式・調達すべて確定済み） |
| FR-04 | 法規チェック | Must | 建ぺい率・容積率・高さは自動計算で合否判定。**容積率の上限は min(指定容積率, 前面道路幅員×法定係数) で判定する**（幅員 12m 未満では指定容積率より厳しくなるのが通例のため。建ぺい率の角地・防火地域緩和は見込まない＝安全側）。北側斜線・道路斜線・日影・自治体条例・**防火/準防火地域**は「要確認フラグ」を出力。対象 1 自治体限定。e-Gov 法令 API は計算エンジンではなく説明文の根拠付け（RAG）に限定使用 |
| FR-05 | 概算見積 | Must | 坪単価テーブルによる概算。「概算」と明記。設備は坪単価への軽い係数として反映する程度。資金計画（ローン試算）はスコープ外（§2.2.2）。部材表は実装方法未定のため本見積で代替（§2.2.1） |
| FR-06 | **自律修正ループ** | **Should** | FR-04／FR-05 の不合格（法規 NG・予算超過）を受けて間取りを修正し再検査する。**本モックの「エージェントである必然性」の中核であり、デモの主役**。無限ループ防止のため最大試行回数を設ける（例: 3 回。超過時は制約緩和の選択肢をユーザーに提示） |
| FR-07 | **機械可読アーティファクト出力** | **Should** | 間取り（部屋・寸法・隣接関係）、要件、制約、法規チェック結果、概算見積を構造化ファイル（JSON 想定）として出力。「業者に渡せる成果物」という本サービスの価値提案（before/after の核）をデモで実体化する。スキーマ詳細は U-04 |
| FR-08 | 人間可読の提案書 | Should | 間取り図（2D 描画）＋見積＋法規結果＋要確認事項＋**敷地の災害リスク**（洪水・土砂・津波・高潮・避難場所。§10 防災情報 API）を 1 つの提案ドキュメントに統合表示 |
| FR-09 | トレードオフ提案 | Should | 予算 vs 要望の衝突時、削る候補（面積・グレード・設備）を提示し交渉する |
| FR-10 | 3D 構想図 | Should | 出力方法は未定 |

### 6.1 入力仕様

| 区分 | 項目 |
|---|---|
| 必須（MVP） | 基本条件（総予算・建物予算・土地有無・エリア）／**敷地の所在地（住所・地番）※土地あり時**／**敷地形状（ポリゴン座標列。デモではプリセット選択可）※土地あり時**／**接道方向・幅員 ※土地あり時**／家族情報（人数・年齢層・将来計画）／間取り要望（部屋数・延床・階数）／優先順位（コスト・広さ・デザイン） |
| 推奨 | **方位（向き・日当たり）**／構造希望／駐車場／こだわり（タグ選択式）／必須空間／ライフスタイル |
| 任意 | 用途地域（自動判定が原則）／インスピレーション画像／設備／性能（耐震・UA 値・ZEH。モックでは省略可） |


- 敷地ポリゴンのデモ用プリセットは**登記所備付地図データ**（G空間情報センター GeoJSON 変換版）から対象自治体の筆を抽出して作成する（§10）。
- 敷地所在地は、モックでは**住居表示の住所**で扱う（地番→座標変換は法務局系データが必要でスコープ外。§10）。
- 敷地形状の入力方法として調査チーム案にある**敷地図アップロード・手書き入力**は、構想としては採用する（画像→ポリゴン化の技術的な実装方法は未定）。モックではプリセット選択で代替する。
- UI 方針: 選択式＋スライダーで簡略化。フリーテキストは補助（AI 補完）。
- 総予算と建物予算の分離は土地なし時のみ必要（土地あり時はほぼ建物予算）。
- 調査チーム案の「ユーザー登録時に必須項目を保存し毎回入力を回避する」は、実装方法は未定。

### 6.2 出力仕様

| 出力 | 対応 FR | 備考 |
|---|---|---|
| 間取り案 | FR-03 | 例: 家族 3 人で生活する間取り。子供が増えた場合にも備える |
| 概算見積 | FR-05 | 「概算」と明記（資金計画・ローン試算はスコープ外。§2.2.2） |
| 法規チェック結果 | FR-04 | 自動判定（建ぺい/容積〔基準容積率含む〕/高さ）＋要確認フラグ（斜線・条例・防火/準防火） |

## 7. 非機能要件（モック水準）

| ID | 項目 | 要件 |
|---|---|---|
| NFR-01 | デモ再現性 | デモシナリオを通しで安定して再現できること（動画撮影に耐える）。LLM 出力の揺れで壊れる箇所は **temperature 0・構造化出力（JSON Schema 強制）・外部呼び出しの記録再生（フィクスチャ）**で固定する（※主要 LLM API にシードによる決定性保証は存在しないため、シードには依存しない） |
| NFR-02 | 応答時間 | 対話応答は数秒オーダー、間取り生成〜ループ完了は分オーダーまで許容（デモで待てる範囲） |
| NFR-03 | 秘匿情報 | API キー等をリポジトリに含めない |
| NFR-04 | コスト | 外部 API・LLM 利用料は研究会活動として許容できる範囲に収める（上限は技術選定時に見積る） |
| NFR-05 | 出力の免責表示 | すべての成果物に「概算・要専門家確認」を明記 |
| NFR-06 | オフライン再生 | 外部 API（GIS・ジオコーディング）・LLM の応答をローカルに記録し、会場のネットワーク断や外部 API 障害時でもデモを完走できる再生モードを持つ（デモシナリオの住所・入力が確定した時点で応答を保存する） |

上記以外の非機能要件（可用性・性能・セキュリティ・運用）はモックのため**意図的に定義しない**。

## 8. システム構成（エージェント＋ツール構成）

### 8.1 方式の再評価

**法規チェックと見積は中身が決定論的計算（GIS 照会＋算術）であり、LLM を介在させる理由がない**。LLM エージェントと呼べるのは判断・生成を担う 2 役のみで、残りは**ツール**である。この再定義は、調査①の結論（LLM が計画・生成し、決定論的な検算が検証する構成が主流）とも一致し、実装も単純になる。

- 「エージェントである必然性」は損なわれない。必然性の根拠は役職の数ではなく、**能動ヒアリング・自律的なツール使い分け・生成→検査→修正の自律ループ**にある。
- 実装上は、2 つの LLM 役割を 1 つの LLM がプロンプト切替で演じる構成でも成立する（技術選定 U-03 で確定）。
- 「生成→検査→修正」の**外側ループの制御は、決定論的なステートマシン（コード）を第一候補**とする（挙動安定化のため）。LLM は各ステップの中身（聞き返し文・修正方針・トレードオフ提案文の生成）を担う。

### 8.2 構成図

```
ユーザー
  │ ①対話（能動ヒアリング: 不足・曖昧を検知して聞き返す）
  ▼
[オーケストレーター（LLM）] ─────────────┐
  │ ②要件確定                            │ ⑤修正指示
  ▼                                      │   ・法規NG → 間取り修正
[間取りデザイナー（LLM）] ◄──────────────┤   ・予算超過 → 面積/グレード調整
  │ ③テンプレ検索 → 局所改変              │   （自律修正ループ・最大N回）
  │   《幾何検算ツール》で都度検証・補正    │
  ▼                                      │
《法規計算ツール》《見積計算ツール》         │
  │ ④合否判定（決定論的）                 │
  ├─ NG ─────────────────────────────┘
  ▼ OK（または上限到達 → トレードオフ提示）
統合提案 ＝ 提案書（人間可読） ＋ 機械可読アーティファクト（JSON）
```

### 8.3 構成要素と責務

| 構成要素 | 種別 | 責務 | 対応 FR |
|---|---|---|---|
| オーケストレーター | LLM エージェント | 対話管理・不足情報の聞き返し判断・ツール/デザイナーへの委譲・ループ制御・トレードオフ提示 | FR-01, 06, 09 |
| 間取りデザイナー | LLM エージェント | テンプレ検索 → 局所改変 → 修正指示の反映（§9.2.2） | FR-03 |
| 敷地照会ツール | 決定論的（MCP 経由） | 住所→座標→用途地域・建ぺい率・容積率の取得。災害リスク情報（防災情報 API 5 種）の取得 | FR-02, 08 |
| 法規計算ツール | 決定論的 | 建ぺい/容積（基準容積率含む）/高さの数値判定・要確認フラグ生成 | FR-04 |
| 幾何検算ツール | 決定論的 | 部屋の重なり・境界内包・面積・隣接整合の検査＋スナップ補正（§9.2.2）。**建物の敷地内自動配置**（境界オフセット等の単純ルール） | FR-03 |
| 見積計算ツール | 決定論的 | 坪単価テーブル×面積＋補正係数・予算超過判定（§9.3） | FR-05 |
| 条文 RAG ツール | 検索 | e-Gov 法令の該当条文を説明の根拠として付与 | FR-04 |
| 描画ツール | 決定論的 | 間取り JSON → 2D 図（SVG/画像）への変換。LLM は描画結果を読み書きしない | FR-08 |

- 外部情報源は MCP 経由の接続先として保持する（既製 MCP サーバー優先。§10）。
- 対外的な「マルチ AI 構成」の訴求は「LLM の役割分担＋自律的なツール使い分け」として維持する（訴求内容と実装が矛盾しない）。
- ヒアリングで確定した要件は会話履歴のべた持ちではなく、**構造化オブジェクト（アーティファクトの要件セクションと同型）に随時固定**して保持する（再現性と、後段ツールへの引き渡しの安定性のため）。

## 9. データ要件

単一 DB では成立せず、役割の異なる**ポリストア**構成

### 9.1 データ層の全体像

| 層 | 形式 | 役割 | モックでの現実解 | 状態 |
|---|---|---|---|---|
| 制約層 | 構造化＋GIS | 土地・用途地域・法規パラメータ（建てられる箱の定義） | 不動産情報ライブラリ＋手入力補完。敷地ポリゴンは登記所備付地図データ由来のプリセット（§10） |
| 事例層 | JSON（部屋ベクトル列＋隣接グラフ＋メタデータ） | 既存優良間取り。「良さ」の源泉。retrieve-and-adapt の検索対象 | テンプレ 15〜30 件（調達確定: §9.2.3） |
| 隣接層 | グラフ（事例層 JSON 内の隣接フィールドとして一体化） | 部屋=ノード、動線・隣接=エッジ。「良い隣接パターン」の知識（水回り集約、寝室=プライベートゾーン、玄関-LDK 関係など） | 隣接ルールを少数キュレーション（改変時の検算・修正指示にも使用） |
| コスト層 | 構造化 | 坪単価・概算見積 | 公的統計から静的テーブル（CSV/JSON）を一度作成（§9.3） |

> モックでのデータ実体は**フラットファイル（テンプレ JSON＋坪単価 CSV/JSON）**であり、DB ミドルウェア（グラフ DB・ベクトル DB・RDB 等）は**導入しない**。「ポリストア」は役割の異なる層の概念整理であって、複数のデータベース製品を立てる意味ではない。

### 9.2 間取り参照データ（U-02）

**表現形式・検索/改変方式（調査① `reference/result_deepresearch1.md`）に続き、調達方法・規模も調査②（`reference/result_deepresearch2.md`）の結果を受けて作成。**

#### 9.2.1 表現形式

間取り 1 件 = 以下を持つ 1 つの JSON とし、**FR-07 機械可読アーティファクトの間取り部分とスキーマを共用**する（内部表現と出力の二重定義を避ける）。

- **部屋ベクトル列** … 部屋ごとに `(部屋ID, タイプ, 中心x, 中心y, 幅, 高さ)`（FloorPlan-DeepSeek 系の表現）
- **隣接グラフ** … 部屋IDペア＋関係タイプ（隣接／ドア接続／方位関係。House-GAN のバブルダイアグラム相当）
- **メタデータ** … 延床・階数・想定家族構成・特徴タグ・境界形状（検索キー用）

設計上の決定（根拠は調査①）:

| 決定 | 理由 |
|---|---|
| 座標・寸法は**整数グリッドに正規化**（半間 910mm モジュールを想定） | LLM の座標ハルシネーション対策（桁のトークン分割問題）。日本家屋の尺モジュールとも整合 |
| 位置・サイズ（ベクトル列）とトポロジ（隣接グラフ）を**別フィールドに明示分離** | LLM は寸法とトポロジを分けて扱う方が修正追従性が高い（ChatHouseDiffusion の設計思想） |
| 各部屋に **ID を付与**し、修正時は「変更対象の部屋のみ再出力、他は据え置き」の**局所編集**をさせる | 1 部屋の変更で全体が壊れる「改変の連鎖崩れ」対策 |
| 非矩形の部屋（L字LDK・階段室等）は**矩形の複合（ポリゴンリスト許容）**で表現 | 単一矩形では表現不能（RPLAN でも約 7% は非矩形）。許容範囲の詳細は U-04 |
| ラスタ画像・SVG は最終描画・ユーザー提示のみに使い、**LLM の読み書き対象にしない** | LLM はラスタ/グリッドの「書き」が弱く、SVG は座標ハルシネーションが起きやすい（間接証拠ベースの判断） |
| LLM の JSON 読み書きには**構造化出力（JSON Schema 強制）**を用いる | スキーマ逸脱・座標ハルシネーションを API レベルで抑止する標準機能（2024 年以降の主要 LLM API で利用可）。幾何検算のリトライ回数を直接減らす（v0.5 追加） |

#### 9.2.2 検索・改変の方式（FR-03 の実現方式）

Graph2Plan（事例検索＋改変の先行研究）の構図の、改変部分を LLM に置き換えた構成とする。

1. **検索（2 段構え）** … ①ハード制約（部屋数・部屋タイプ・階数）でフィルタ → ②延床面積・境界形状・特徴タグの類似度でランク。テンプレ十数件の規模ではベクトル DB は不要で、メタデータの単純スコアリングで足りる。
2. **改変** … LLM が入力条件（家族構成・要望・敷地制約）に合わせてテンプレ JSON を局所編集。
3. **幾何検算（決定論的）** … 部屋の重なり／敷地境界のはみ出し／面積合計／隣接整合をルールベースで検査。**重なり > 0 または主要制約の充足率 < 90% なら自動リトライ**（FR-06 の法規・予算ループとは別の、間取り生成内部の内側ループ）。「主要制約」の列挙と充足率の算定式は U-04 で定義する。面積検査は壁厚分の許容誤差を持たせる（部屋面積の合計は延床と厳密には一致しない）。
4. **再アライメント** … 検算で検出した軽微な崩れは、境界辺・隣接辺へのスナップ等のルールベース処理で補正する（LLM 単体では連鎖崩れを吸収できないため）。

段階的検証の方針: まず in-context 改変＋検算リトライで制約充足率・構造妥当性を計測し、実用水準（充足率 90% 目安）に届かない場合のみ後処理強化や学習ベース手法を検討する（調査①の推奨手順）。

既知の限界（リスクとして管理）: retrieve-and-adapt は**テンプレから遠い要望に弱い**。十数件では被覆が薄いため、フィルタ緩和・複数テンプレ参照をフォールバックとし、デモシナリオはテンプレ被覆内で設計する（→ §12）。

#### 9.2.3 調達方法・規模【確定・調査②反映】

**案 A（自前キュレーション）を採用**する。調査②により、参照ソースの実在と権利上の安全性が裏付けられた。

- **調達手順**: 公開間取りプランを人が閲覧し、部屋構成・面積・隣接関係のみを抽象化して §9.2.1 の JSON に構造化する（LLM 補助＋人手レビュー）。**図面画像は保存・転載しない**（テキスト情報としてのみ利用）。
- **規模**: 15〜30 件。ペルソナ帯（延床 25〜40 坪、3LDK〜5LDK、平屋/2 階建て）をカバーするよう選定する。
- **参照ソース**（調査②で確認済みの主な候補）:

| ソース | 内容 | 位置づけ |
|---|---|---|
| メガソフト「間取り・注文住宅プラン集」 | 戸建て 114 戸分〜（500 戸予定）。無償 DL 可・用途を問わず利用可（調査②の報告） | **主ソース候補**。※利用規約の原文確認を実装着手前に行うこと（下記） |
| ミサワホーム「間取り集 500 プラン」／住友林業 Forest Selection／Madree／大和ハウス ほか | 各社 Web で数百〜2,000 件超を公開 | 閲覧参考（構成・定石の妥当性確認用） |
| 住宅設計の定石資料（住宅金融支援機構 技術基準、設計実務書籍等） | 寸法・動線の設計基準 | LLM 生成テンプレの整合性チェック用 |

- **権利上の根拠**（調査②）: 知財高裁判例（メゾン A 事件）により間取り図の著作物性は認められにくく、**部屋数・配置・面積等は著作権保護の対象外の「事実」**と解される。安全策として①図面画像を保存しない、②情報のみ抽出、③各サイトの利用規約を確認しスクレイピングをしない（人手閲覧）、を徹底する。
- **要確認（実装着手前）**: メガソフトの「利用可」は調査②の二次情報のため、**規約原文を実装チームで直接確認**する。確認できない場合も閲覧参考＋LLM 生成主体（従前の案 A）で成立するため、ブロッカーにはならない。

### 9.3 コスト層（坪単価テーブル）【確定・調査③反映】

公的統計から**静的テーブル（CSV/JSON）を一度作成**して使う。リアルタイム API 接続はしない。

- **主ソース**: 住宅金融支援機構「フラット35利用者調査」（注文住宅・都道府県別の平均建設費・延床面積を Excel 公開。2024 年度: 全国平均で建築費約 3,932 万円／118.5 ㎡ ≒ **約 110 万円/坪**）。実際の注文住宅の成約実績に基づくため、ユーザーの体感相場に最も近い。
- **クロスチェック**: 国税庁「地域別・構造別工事費用表」（都道府県×構造別、無償 HTML）、国交省「建築着工統計」（e-Stat API、都道府県×構造別の工事費予定額/床面積）。
- **年次補正**: 元データの年次を明記し、必要に応じ国交省「建設工事費デフレーター」で直近相当へ補正する。
- **補正係数**（調査③の相場観。テーブルに係数列として持つ）: 階数（2 階建て=1.00、3 階建て≒1.05）／構造（木造=1.0 基準、鉄骨・RC は 1.4〜2.0）／設備（太陽光 4kW≒＋115 万円、全館空調≒＋100〜300 万円、ZEH 級断熱≒＋10〜20 万円/坪）。
- **注意（ソース間乖離）**: 国税庁表由来の坪単価（≒76 万円/坪）とフラット35 由来（≒110 万円/坪）は**費用範囲の定義が異なり約 4 割乖離**する。見積出力には採用ソースと「本体工事費のみ／諸経費別」の別を必ず明記する（NFR-05 と連動）。

## 11. 受入基準（デモ完了条件）

デモシナリオ（§5）確定後に具体化するが、シナリオに依らない基準を先に定める。

| ID | 基準 | 対応 FR |
|---|---|---|
| AC-01 | 不足入力に対しエージェントが自律的に聞き返し、対話で要件が確定する場面が示せる | FR-01 |
| AC-02 | 住所（地番）から用途地域・建ぺい率・容積率が自動取得される | FR-02 |
| AC-03 | 入力条件に応じた間取り案が生成・表示される | FR-03 |
| AC-04 | 法規チェックが合否と要確認フラグを出力する | FR-04 |
| AC-05 | **法規 NG または予算超過 → 自動修正 → 再チェック合格、のループが 1 回以上デモ中に観察できる** | FR-06 |
| AC-06 | 機械可読アーティファクト（JSON）が出力され、中身が間取り・制約・見積・チェック結果を含む | FR-07 |
| AC-07 | 上記が 1 本のシナリオとして通しで実演でき、動画撮影に耐える | NFR-01 |

- AC-05 の成立には「初回生成が確実に NG になる仕込み」をデモ台本（§5）に含めること（自然に任せると一発合格でループが映らないリスクがある）。
- 間取りの「良さ」の判定は、モックでは「幾何検算合格＋隣接ルール充足＋実装チームの目視レビュー」とする（定量的な品質評価はスコープ外）。

## 12. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| テンプレ構造化の品質ばらつき（人手・LLM 補助の抽出誤り） | 事例層の質が低いと生成品質に直結 | JSON スキーマによる機械検証＋幾何検算ツールをテンプレ登録時にも通す。数件先行作成してレビュー基準を作る |
| メガソフト プラン集の利用規約が想定と異なる | 主ソース候補の差し替え | 規約原文を実装着手前に確認（§9.2.3）。不可でも閲覧参考＋LLM 生成主体で成立するためブロッカーにならない |
| 対象自治体の GIS データが期待どおり取れない／古い | FR-02/04 が成立しない・誤る | U-01 の自治体決定前に、不動産情報ライブラリの当該データ取得を技術検証（スパイク）する。**取得値と自治体公式の都市計画図の目視照合を含める** |
| 地理空間 MCP Server（α版）の仕様変更・停止 | FR-02 が動かなくなる | バージョンのピン止め（コミット固定）＋応答の記録再生（NFR-06） |
| デモ会場のネットワーク断・外部 API 障害 | デモ不成立 | オフライン再生モード（NFR-06）。GIS・ジオコーディング応答はデモ住所確定後に保存する |
| LLM 出力の揺れでループが収束しない | デモ再現性（NFR-01）毀損 | 決定論的な幾何検算＋自動リトライ（§9.2.2）、最大試行回数、修正指示のテンプレ化、デモ用フォールバック（成功パスの固定） |
| retrieve-and-adapt の被覆限界（テンプレから遠い要望で破綻） | デモ中の想定外入力で品質低下 | デモシナリオはテンプレ被覆内で設計。フォールバックとしてフィルタ緩和・複数テンプレ参照（§9.2.2） |
| 「適法と誤解される」出力 | 研究会成果物としての信頼性・責任問題 | 全出力に免責明記（NFR-05）。スライドにも記載 |
| デモシナリオ協議（調査チーム）の遅延 | 台本・データ準備が後ろ倒し | §5 のチェックリストを協議アジェンダとして先渡しする |
