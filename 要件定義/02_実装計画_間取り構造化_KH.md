## Context

現状の間取り出力は `FloorPlan`（`app/schemas/floorplan.py`）が全フィールド文字列で、`Room.area` が `"18畳"`、`total_floor_area` が `"約100㎡（約30坪）"` という表示用テキストしか持たない。結果として：

1. **デモが「文章の壁」になる** — `frontend/index.html:588` の `renderPlans` はテキストカードのみ、`plan.rooms.slice(0, 6)` で6室打ち切り。最重要成果物（スライド・デモ動画）で図が出ない。
2. **出力の揺れが検出できない** — `planning_agent.py:81-92` は `format="json"`（JSONモード）＋手書き `json.loads`。JSON Schema 強制ではないので、フィールド欠落・面積の不整合が素通りする。
3. **面積の数値の供給元がない** — 法規担当の建ぺい率判定には**建築面積（1階フットプリント）**、見積担当には**延床面積の数値**が必要だが、現状は文字列しかなく、両者が各自で文字列パースを書くと値がズレる。

本作業で、間取りを KH案 §9.2.1 準拠の座標付き JSON に構造化し、幾何を**完全決定論的**に生成・検算して階ごとの SVG で描画する。あわせて面積の単一の真実の源を提供し、機械可読アーティファクト（KH案 FR-07）を出力する。

### 設計の中心的な判断：座標を LLM に出させない

「7〜8個の矩形を隙間なく重なりなしに矩形へ詰める」は矩形パッキング（制約充足問題）で、自己回帰生成は構造的に解けない。`docs/reference/result_deepresearch1.md` の「type/location は正確だが **size/location の精密さに課題**」がこれで、モデルを大きくしても解決しない（14B → 70B → GPT-4 で変わるのは崩れの程度だけ）。

したがって役割を分ける：

| 担い手 | 責務 |
|---|---|
| LLM（qwen2.5:14b） | 部屋構成 — 部屋タイプ・目標面積・階。14B で十分こなせる領域 |
| 決定論的レイアウトエンジン | 座標 — 再帰二分割（BSP）で**重なり0・隙間0を数学的に保証** |

`SUMAI_LAYOUT_MODE=llm` で LLM に座標を出させる経路も併設し、検算 NG なら決定論へフォールバックする（実測用オプション。既定は `deterministic`）。

## 座標系・スキーマ（KH案 §9.2.1 準拠）

- **グリッド**: 910mm（半間モジュール）。`CELL_AREA_M2 = 0.8281 m²`、`1畳 = 2セル = 1.6562 m²`
- **原点**: 敷地南西角。部屋・フットプリント・敷地をすべて同一のグローバル座標系（グリッド単位）で保持 → 敷地内包チェックと SVG 描画が自明になる
- **格納形式**: 南西角 `(x, y)` ＋ `(w, h)` を**グリッド単位の整数**で保持
- **公開形式**: `cx = x + w/2`, `cy = y + h/2` を `@computed_field` で提供（KH案の「中心x, 中心y」。奇数幅で `.5` になるため格納は整数角、公開は中心）
- **方位**: モデル座標系は y が北向きに増加。SVG 描画時に上下反転（南＝下）

```
app/schemas/geometry.py
  GRID_MM = 910, GRID_M, CELL_AREA_M2, TATAMI_M2, TSUBO_M2
  FLOOR_HEIGHT_M = 2.9, ROOF_RISE_M = 1.2      # KH案 U-04「階高の既定値」を確定
  ROOM_TYPES: Final[tuple[str, ...]]            # 固定語彙（下記）
  ROOM_TYPE_ALIASES, CIRCULATION_TYPES
  normalize_room_type(raw) -> tuple[str, str | None]   # (正規化型, 警告)

  RoomSpec         room_id, room_type, label, target_area_m2, floor   # エンジンへの入力（座標なし）
  RoomBox          room_id, room_type, label, x, y, w, h, floor, target_area_m2
                     → cx / cy / area_m2 / area_tatami / aspect
  Adjacency        a, b, relation("adjacent"|"door"|"stair"), shared_len_grid, floor
  SiteBoundary     preset_key, width_grid, depth_grid, road_side, road_width_m, setback_grid
                     → width_m / depth_m / area_m2 / area_tsubo
  FloorGeometry    floor, footprint_x/y/w/h, rooms[], adjacencies[] → footprint_area_m2
  BuildingGeometry schema_version, grid_mm, floor_height_m, roof_rise_m, site,
                   floors[], inter_floor_adjacencies[],
                   layout_source("deterministic"|"llm"|"deterministic_fallback"), notes[]
```

**固定語彙 `ROOM_TYPES`**（これがエンジンを決定論にする要）:

```
LDK, リビング, ダイニング, キッチン, パントリー,
主寝室, 寝室, 子供部屋, 書斎, 和室,
浴室, 洗面脱衣, トイレ,
玄関, ホール, 階段, 廊下,
```

`ROOM_TYPE_ALIASES` で LLM の揺れを吸収（`リビングダイニングキッチン→LDK`、`洗面所/脱衣室→洗面脱衣`、`ウォークインクローゼット→WIC`、`納戸→収納`、`洋室→寝室`、`ワークスペース→書斎`、`土間→玄関` など）。未知の値は `その他` にマップして `notes` に記録し、例外は投げない（NFR: 落とし穴の握りつぶしはしないが、描画は必ず成立させる）。

## レイアウトアルゴリズム（`app/tools/layout_engine.py`）

### ① フットプリント

- `W_grid = round(sqrt(A_1F × 1.25 / CELL_AREA_M2))`（幅:奥行 ≒ 1.25:1）、`W ≥ 6` にクランプ
- `D_f = round(A_f / (W × CELL_AREA_M2))`、`D ≥ 5` にクランプ
- **幅 W は全階共通、奥行きのみ階ごとに可変** — 構造的に妥当で、かつ階段位置の整合に効く
- 丸めで生じた面積差は `footprint_area_error_pct` として検算結果に残す（黙って捨てない）

### ② ホール帯（階段の階間整合 / KH案 U-04）

東側に幅 `HALL_W = 2` グリッド（1.82m）の帯を全階・全奥行で予約し、**南端（y=0）から固定アンカーで**割り付ける：

| y範囲（帯内・相対） | 1階 | 2階 |
|---|---|---|
| `[0, 2)` | 玄関 | ホール（階段上部の踊り場） |
| `[2, 4)` | **階段** | **階段**（同一矩形） |
| `[4, D_f)` | 廊下 | ホール |

階段は全階で `(x = footprint_x + W - 2, y = footprint_y + 2, w = 2, h = 2)` に固定 → **階間整合が構造的に成立**（`D_f` が階ごとに違っても影響しない）。平屋は階段を置かず玄関＋ホールのみ。副産物として廊下が入り、間取りとして読める図になる（廊下のない図は間取りとして不自然に見える）。

### ③ 部屋の BSP 分割

残矩形 `(W-2) × D_f` を、ゾーン順を保った再帰二分割で分ける。

**ゾーン順**（連続グループが空間的にまとまるので、これが隣接品質を決める）

- 1階: `LDK → リビング → ダイニング → 和室 → キッチン → パントリー → 洗面脱衣 → 浴室 → トイレ → 収納 → その他`
- 2階: `主寝室 → WIC → 子供部屋 → 寝室 → 書斎 → トイレ → 収納 → バルコニー → その他`

```
bsp(rect, rooms):
  len(rooms) == 1 → rect をその部屋に割り当てて終了
  total = Σ target_area
  k     = 累積面積が total/2 を初めて超える最小の index（1..len-1）
  frac  = Σ rooms[:k] / total
  軸    = rect の長辺（アスペクト比が自然に 1 へ寄る）
  cut   = clamp(round(frac × 軸長), 1, 軸長 - 1)      # グリッド整数に丸め
  bsp(南/西側, rooms[:k]) ; bsp(北/東側, rooms[k:])
```

- 再帰分割なので**隙間なし・重なりなし・全面被覆が保証される**（検算は「起きないことの確認」＝回帰ガードとして機能する）
- ゾーン順の先頭が南西に落ちるため LDK が自然に南面する
- **ガード**: `軸長 < 2` なら他軸へ切替、両軸とも不可なら最小の部屋を隣接部屋へ統合して `notes` に記録（ゼロ幅部屋を絶対に作らない）

### ④ 隣接グラフの導出

矩形の辺共有から決定論的に生成する。

```
touch_x    = (a.x + a.w == b.x) or (b.x + b.w == a.x)
overlap_y  = min(a.y+a.h, b.y+b.h) - max(a.y, b.y)
隣接        = (touch_x and overlap_y >= 1) or (touch_y and overlap_x >= 1)
shared_len = その重なり長（グリッド）
relation   = "door"  if 一方が動線室（玄関/ホール/階段/廊下） or shared_len >= 2
             "adjacent" otherwise
```

階段矩形が全階で一致することを利用して、階間エッジ `relation="stair"` を張る。**KH案の隣接グラフが LLM を介さずタダで手に入る。**

### ⑤ 敷地配置（`app/data/site_presets.py`）

グリッド整数の整形地プリセット（30 / 35 / 40 / 50坪、接道方向・幅員つき）。

- 北・東・西に `SETBACK = 1` グリッド（0.91m ≥ 民法234条の50cm）を確保
- 建物を幅方向中央・南寄せに配置。南の残余がアプローチ／駐車スペース
- 収まらなければ次に大きいプリセットへ自動繰り上げし `notes` に記録（KH案 §8.3「建物の敷地内自動配置」）
- プリセットは `requirements.land_info` の `(\d+)\s*坪` 正規表現から選択、なければ既定 `35坪整形地`。`SUMAI_SITE_PRESET` で明示上書き可
